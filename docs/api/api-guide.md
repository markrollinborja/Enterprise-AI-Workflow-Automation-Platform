# API Guide

This is a committed reference to the REST API — grouped by resource, with the
auth requirement and an example for each group. It exists so someone can read
what the API does without running the app. For the exhaustive, always-current
schema (every field, every response model, try-it-out), run the backend and
open **`http://localhost:8000/docs`** (Swagger UI, generated by FastAPI
directly from the route definitions — it cannot drift out of sync with the
code the way a hand-written doc can). This guide is the map; Swagger is the
territory.

All endpoints are relative to the backend's base URL (`http://localhost:8000`
in local Docker Compose). All request/response bodies are JSON.

## Authentication

Every route except `POST /auth/login`, `GET /health`, `GET /health/ready`,
and `POST /webhooks/jira` requires a bearer token:

```
Authorization: Bearer <token>
```

Tokens come from `POST /auth/login` and are valid for 8 hours (no refresh
flow — see [`docs/architecture/authentication.md`](../architecture/authentication.md)
for why that's a deliberate V1 simplification, not an oversight). A request
with a missing, expired, or invalid token gets `401`. A request from a
correctly-authenticated user whose role doesn't allow the action gets `403`
— enforced server-side in the FastAPI dependency layer
(`app.api.deps.require_role`), never left to the frontend to hide a button.

**Example — log in and call an authenticated route:**

```powershell
$login = Invoke-RestMethod -Method Post -Uri http://localhost:8000/auth/login `
  -ContentType "application/json" `
  -Body '{"email":"hr.coordinator@cordant.io","password":"changeme123"}'

Invoke-RestMethod -Uri http://localhost:8000/employees `
  -Headers @{ Authorization = "Bearer $($login.access_token)" }
```

## Auth

| Method | Path | Auth | Notes |
|---|---|---|---|
| POST | `/auth/login` | none | Body: `{email, password}`. Returns `{access_token, token_type}`. |
| GET | `/auth/me` | any authenticated user | Returns the caller's own user record. |

## Employees

| Method | Path | Auth | Notes |
|---|---|---|---|
| GET | `/employees` | any authenticated user | Full directory — read access is intentionally broad, like most internal org directories. |
| GET | `/employees/{employee_id}` | any authenticated user | |
| POST | `/employees` | HR or Administrator | See body shape below. |
| PATCH | `/employees/{employee_id}` | HR or Administrator | Partial update — all fields optional. |

**Example — create an employee** (`POST /employees`):

```json
{
  "first_name": "Jamie",
  "last_name": "Rivera",
  "work_email": "jamie.rivera@cordant.io",
  "job_title": "Software Engineer II",
  "department_id": "3f2b6c1a-....",
  "manager_id": "9a11d0e4-....",
  "employment_type": "full_time",
  "start_date": "2026-08-10",
  "location": "Austin, TX",
  "risk_level": "low"
}
```

## Applications

| Method | Path | Auth | Notes |
|---|---|---|---|
| GET | `/applications` | any authenticated user | The seeded catalog of systems employees can request access to (each with a `risk_level`) — this is what makes access-request risk classification a deterministic lookup, not an AI guess. No write route in V1; see `ApplicationResponse`'s docstring. |

## Access Requests

| Method | Path | Auth | Notes |
|---|---|---|---|
| POST | `/access-requests` | any authenticated user with a linked employee record | Starts the `software_access_request` workflow. `employee_id` is *not* a body field — it's derived server-side from the caller's own token, so no user can submit a request as someone else. |

**Example:**

```json
// POST /access-requests
{
  "application_id": "8d4e2a10-....",
  "justification": "Need Salesforce access to update opportunity records for the Q3 renewal push."
}
```

Response includes the rules engine's decision (`computed_risk_level`,
`auto_approved`) and where the workflow instance currently stands.

## Approvals

| Method | Path | Auth | Notes |
|---|---|---|---|
| GET | `/approvals` | any authenticated user | Returns only what's relevant to the caller (assigned-to-them, their role's pool, or everything for Administrators) — the filtering *is* the access control, no separate role gate needed. |
| POST | `/approvals/{approval_request_id}/decide` | Manager, IT, Security, or Administrator | Body: `{decision: "approved"\|"rejected", notes?}`. Coarse role gate at the route; fine-grained "is this actually yours" check happens in the service layer against `assigned_user_id`. |

## Dashboard (Administrator only)

Every route below requires the Administrator role — matches the project's
own role spec ("Administrator: View all workflows, View audit logs"), not an
invented cross-department visibility rule.

| Method | Path | Notes |
|---|---|---|
| GET | `/dashboard/summary` | Aggregate counts: active/completed/failed workflows, pending approvals, by-department/by-type breakdowns. |
| GET | `/workflow-instances` | Optional `?status=` filter (e.g. `?status=failed` — also what the Failed Workflows page uses). |
| GET | `/workflow-instances/{instance_id}` | Full detail: input data, steps, approvals, AI recommendations, MCP tool calls, errors. |
| GET | `/audit-log` | Composed timeline across workflow events, approval decisions, AI executions, MCP tool calls, and manual retries — synthesized at read time, not a dedicated audit table (see [`data-model.md`](../architecture/data-model.md)). |

## Workflow instance actions

| Method | Path | Auth | Notes |
|---|---|---|---|
| POST | `/workflow-instances/{instance_id}/steps/{step_key}/retry` | Administrator only | Resets a `FAILED` step to `PENDING` and re-runs the engine. `404` if the instance/step doesn't exist, `409` if the step isn't currently `FAILED`. |

## Webhooks

| Method | Path | Auth | Notes |
|---|---|---|---|
| POST | `/webhooks/jira` | HMAC-SHA256 signature (`X-Hub-Signature-256` header, shared secret in `JIRA_WEBHOOK_SECRET`) — **not** a JWT bearer token | Confirms fulfillment of a Jira ticket this system created earlier in a workflow. Not the workflow's *trigger* (contrast with Project #1) — it closes the loop on one already-running step. See [ADR-0010](../decisions/0010-jira-fulfillment-confirmation-via-webhook.md). |

## Health

| Method | Path | Auth | Notes |
|---|---|---|---|
| GET | `/health` | none | Liveness only — never touches the database, stays fast even if Postgres is slow. |
| GET | `/health/ready` | none | Liveness + a real `SELECT 1` against Postgres. |

## Error shape

All errors return a consistent JSON body:

```json
{ "detail": "human-readable message" }
```

with the HTTP status carrying the machine-readable meaning: `400`
(validation), `401` (missing/invalid token), `403` (wrong role), `404` (not
found), `409` (conflicting state — e.g. retrying a step that isn't
`FAILED`), `422` (Pydantic schema validation failure on the request body).
