# ADR-0009: Application Catalog is Internal Reference Data, Not an Okta Integration

**Status:** Accepted — 2026-07-27

**Context:** Phase 8 needed a source of truth for which internal applications exist and how risky each one is, to drive the software-access-request workflow's risk classification. A real enterprise would very plausibly source this from an identity provider's app catalog (Okta, in particular, since it's the most common free-tier-available option) rather than hand-maintaining it. Before building `Application` as a plain internal table, we evaluated integrating Okta directly.

**Decision:** `Application` is a small internal table (`id, name, description, risk_level, created_at`), seeded like `Department`/`Employee` — not sourced from Okta or any external IdP, and not wrapped behind MCP.

**Alternatives considered:**

- **Okta integration** (call Okta's API to list assigned/available apps, or use it as the actual source of `risk_level`) — rejected for three reasons. First, scope: this project automates and integrates *around* enterprise systems, it doesn't stand up a second one — Okta's app catalog has no native concept of "risk level" anyway, so integrating it wouldn't remove the internal `risk_level` classification, it would just add a second data source to keep in sync with the first, for a field Okta doesn't even provide. Second, architecture: the rules engine (`services/rules`) is explicitly designed as a dependency-free leaf — no DB, no I/O, unit-testable with zero setup (ADR-0004). A live Okta call anywhere upstream of it would break that guarantee for one of V1's two workflows while leaving onboarding's rules untouched, an inconsistency with no real payoff. Third, cost/complexity-for-hiring-value: getting a real Okta developer org talking to this project buys a checkbox ("integrates with an IdP") that doesn't map to any of the target roles' actual day-to-day work more than the MCP integrations (Jira/Slack/Calendar) already do, for real implementation cost (OAuth setup, API quirks, another thing that can fail in a demo).
- **Wrapping the Application catalog lookup in an MCP tool** (e.g. `lookup_application`) even though it stays an internal table — rejected as decorative. MCP is reserved for genuine external actions with an audit/least-privilege story (see `docs/architecture/mcp-architecture.md`); a deterministic read of our own Postgres table gains nothing from an MCP indirection layer except a fake appearance of "using MCP more."

**Consequences:** The application catalog is exactly as demoable and exactly as "enterprise-realistic" as the employee directory — reference data an HR/IT team maintains, not a live external dependency. Cutting Okta also cuts the `owner_role` column from the original Phase 1 sketch of `Application` (see `docs/architecture/data-model.md`): it existed to eventually support dynamic per-application approval routing, a real feature this project doesn't build in V1. If a future phase adds real dynamic routing (a genuine hiring-relevant feature — "the approver depends on which system you're requesting, not a hardcoded role"), that's the point to revisit both this table and whether an IdP integration earns its cost. For now: rules before AI, and rules before integrations that don't change any of the rules.
