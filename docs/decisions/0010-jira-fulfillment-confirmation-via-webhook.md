# ADR-0010: Jira Fulfillment Confirmation via Webhook — Additive to Approval, Not a Replacement

**Status:** Accepted — 2026-07-27

**Context:** The workflow engine's `mcp_tool` steps (`create_it_tasks`, `create_fulfillment_task`) currently mark themselves `completed` the moment the Jira ticket-creation call succeeds — the engine never learns whether IT actually finished the work. Real IT ticket completion should confirm the underlying task was carried out, not just requested. Two designs were considered for how Jira's ticket-completion signal reaches this system.

**Decision:** Jira ticket completion becomes a *fulfillment confirmation*, layered on top of the existing approval flow, not a substitute for it. The sequence stays: approval happens first (through our own approval inbox, exactly as built in Phase 7) → the Jira ticket is created only after approval → the step then waits for a Jira webhook confirming the ticket transitioned to Done before the workflow is allowed to complete. This is scoped into Phase 10 (MCP Server and Tools), since it depends on the real (non-stub) Jira MCP tool existing first.

**Alternatives considered:**

- **Jira completion *replaces* the approval step** (IT never uses our approval inbox — marking the ticket Done is the approval decision itself). Rejected for V1: it requires creating the Jira ticket *before* approval, inverting the "approve, then act" ordering every other step in this system follows (manager, IT, and security approvals all gate the action that follows them, never the reverse). Making exactly one step type behave backwards is a real inconsistency to explain and test, for a UX convenience (IT doesn't have to also click "approve" in our system) that doesn't outweigh the cost of an inconsistent state model. Revisit if a future phase redesigns the approval engine around "approval can be satisfied by an external system event," generally, rather than special-casing Jira.
- **No completion tracking at all** (status quo: ticket creation succeeding is treated as done). Rejected: it's a real reliability gap this project's own principles call out — Principle 4 wants "integration succeeded" distinguished from "the actual business outcome happened," and this project's Task/fulfillment tracking should reflect whether IT finished, not just whether a ticket exists.

**Consequences:** Requires a genuinely new piece of the state model — a step that's `completed` only on an inbound signal, not a synchronous return value or a scheduled retry — and a public-facing webhook endpoint with signature verification (Jira's webhook payloads must be authenticated, not trusted on receipt). Locally, this means a tunnel (e.g. ngrok) for any session that needs to demo it live, since ADR-0007 keeps V1 unhosted. Design specifics (step schema, how an inbound Jira issue key correlates back to a specific `WorkflowStepInstance`, idempotency for duplicate webhook deliveries) are deferred to Phase 10's own "explain before coding" pass — this ADR fixes the *shape* of the decision (additive, not a replacement for approval), not the implementation.

**Also worth naming directly:** this does not duplicate Project #1's Jira-webhook pattern, even though both projects end up with a `/webhooks/jira` endpoint. Project #1's webhook *is* the trigger for its automation — a Jira ticket existing is what starts the whole pipeline. Here, the webhook closes the loop on a task this system already created as one step inside a larger, already-orchestrated, multi-department workflow — confirmation of fulfillment, not the initiating event. That distinction is the actual talking point if this comes up in an interview: reacting to Jira vs. orchestrating Jira as one integration among several inside a bigger process.
