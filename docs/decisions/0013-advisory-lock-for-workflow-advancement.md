# ADR-0013: Postgres Advisory Lock for Workflow Advancement, Not `SELECT ... FOR UPDATE`

**Status:** Accepted — 2026-07-29

**Context:** `advance_workflow` is called from two different places on the same instance: synchronously from an API request right after an event that should move a workflow forward (approval decided, Jira webhook confirming fulfillment), and from the worker's poll loop (`app/workers/runner.py`) recovering anything `running`/`waiting_external` and due. ADR-0002 assumed `SELECT ... FOR UPDATE SKIP LOCKED` would be the eventual fix for a worker/API race on the same instance, deferred to Phase 13. Building it surfaced a problem with that assumption: `advance_workflow`'s critical section — the loop that walks each step in order — commits after *every* step transition (`db.commit()`, several times per call), for durability: if the process crashes mid-loop, whatever was already committed for earlier steps in that same call stays committed. A `SELECT ... FOR UPDATE` row lock releases at the very first of those commits, not at the end of the function — so it wouldn't actually protect the rest of the loop, including the part where a step sits `RUNNING` while an OpenAI or MCP call is in flight. That gap is exactly what produced a real, observed bug: `InvalidTransitionError: Cannot transition from 'running' to 'running'`, from the worker's poll grabbing the same instance the API was still mid-flight on.

**Decision:** Use a Postgres session-level advisory lock (`pg_advisory_lock` / `pg_try_advisory_lock` / `pg_advisory_unlock`), keyed by `hashtext(instance_id::text)`, held for the entire `advance_workflow` call regardless of how many `db.commit()`s happen inside it. Two entry points share the same locked implementation (`_advance_workflow_locked`): `advance_workflow` blocks until it acquires the lock (every synchronous caller — `start_workflow`, `resume_workflow_step`, `confirm_external_completion` — needs a definitive result to return to its own caller, so blocking is correct there), and `try_advance_workflow` (the worker's poll loop only) attempts the lock non-blockingly and simply skips the instance for this tick if it's already held, trusting the next 3-second poll to retry.

**Alternatives considered:**
- `SELECT ... FOR UPDATE SKIP LOCKED` — the originally planned approach; rejected once the multi-commit shape of the critical section was actually examined (see Context). Would have needed restructuring `advance_workflow` into a single transaction with one commit at the end to work correctly, which trades away the existing crash-durability property (partial progress within one call surviving a crash) for locking convenience — a worse tradeoff than switching lock primitives.
- Removing the API's inline `advance_workflow` call entirely, letting only the worker ever advance a workflow — simpler, no locking needed at all. Rejected: it would add up to a 3-second visible lag between an admin clicking "Approve" and the workflow actually moving to its next step in the UI, which matters for how the demo *feels* even though it wouldn't affect correctness. Kept the instant inline advance and paid for it with locking instead.
- A dedicated `WorkflowInstance.locked_by`/`locked_at` column (application-level locking) — rejected as more code than a built-in Postgres primitive, and it reintroduces the exact "did the lock-holder crash and never release it" problem advisory locks already solve at the connection level.

**Consequences:** The observed race is closed for the actual failure mode seen (worker vs. inline API call), and incidentally also protects against two near-simultaneous API requests racing the same instance (defense in depth beyond what the frontend's own button-disabling already prevents in the common case). Known, accepted limitations, both explicit rather than silent: (1) `hashtext()` collapses a UUID into a 32-bit key — a hash collision between two different instances' lock keys is possible in principle, negligible at this project's demo scale (never more than a handful of concurrent instances), not worth a composite two-key lock to close. (2) This does not solve horizontal worker fan-out by itself — a second worker replica would still correctly skip locked instances via `try_advance_workflow`, so ADR-0002's "leaves room for worker replicas later" claim still holds, just through a different mechanism than originally planned.

**Correction found in testing, before this ADR ever shipped:** the first implementation acquired and released the lock using `db` — the same SQLAlchemy `Session` passed in to run the rest of the function — on the theory that "session-level" meant "tied to that Session object." It doesn't: Postgres ties the lock to the *physical* backend connection that issued it, and a default SQLAlchemy `Session` (`autocommit=False`) checks its connection back into the pool at every `db.commit()`, possibly getting a different one for whatever runs next. `_advance_workflow_locked` commits several times per call, so the connection actually holding the lock could differ from the one the later unlock ran on — orphaning the lock, held forever by an idle pooled connection, with the very next attempt to lock that instance (e.g. a second `resume_workflow_step` call in the same request-handling session — the manager-approval-then-IT-approval sequence every onboarding runs) hanging permanently. Caught by the test suite hanging on exactly that sequence, not by design review. Fixed by acquiring and releasing the lock on a dedicated `engine.connect()` `Connection`, opened fresh and held (not committed, just closed) for the whole call — decoupled entirely from however many times `db` itself commits in between. See `app/services/workflows/service.py`'s `advance_workflow` docstring for the corrected version.
