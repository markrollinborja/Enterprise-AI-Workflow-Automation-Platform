# ADR-0014: Role-Pool Approvals Fan Out to Every Holder of the Role, Not Just In-App

**Status:** Accepted — 2026-07-31

**Context:** `_create_approval_request` (in `app/services/workflows/service.py`) originally only pushed a notification (in-app + Slack) when a step's approver resolved to one specific person — `manager_approval`, which `_resolve_approver` maps to the employee's actual manager via `Employee.manager_id`. IT and Security approvals have no natural single owner in this data model (`assigned_user_id` is `None`, a "role pool" any user with that role can pick up via their Approvals Inbox), so the original implementation deliberately skipped notifying anyone for those — the comment at the time reasoned that fanning out to every user with a role could get spammy at real-company scale, with no per-recipient "is this still relevant to me" state once one of them acts.

Real-mode end-to-end testing (running both workflows against live Jira, Slack, and Calendar rather than mocks) surfaced the actual cost of that decision: a manager approves onboarding, and the chain visibly stops there from the approver's point of view — nothing tells IT their step just opened up. They'd only ever find out by opening the Approvals Inbox unprompted. For a demo whose entire value proposition is "approval chains that actually move," a chain that goes silent after step one reads as broken even though the backend state is correct.

**Decision:** When `assigned_user_id` is `None` (a role-pool approval), notify every `User` holding that role instead of notifying no one. Added `user_repo.list_by_role(db, role)` and changed `_create_approval_request` to build its notification recipient list as `[assignee]` when there's a single resolved owner, or the full role-pool list otherwise — the rest of the function (in-app + Slack via the same `notification_service.notify()` call, `send_slack=True`) is unchanged, just looped over more than one recipient in the pool case.

The original spam concern doesn't disqualify this for the actual data this project ever runs against: this project's demo roster has exactly one user per role (one IT user, one Security user), so "notify everyone with the role" and "notify the one specific person who'd obviously pick this up" are the same operation here. A real multi-person IT team would need a different design (claim/assignment semantics, or notifying only on a delay if nobody's claimed it) — explicitly out of scope for V1, noted as a real limitation rather than solved silently.

The premature-notification risk this decision could introduce doesn't apply: `_create_approval_request` only runs the moment a step actually transitions to `waiting_approval` (see its own docstring), and the workflow engine advances steps strictly in sequence — the IT step's `ApprovalRequest` row, and therefore its notifications, cannot exist before the manager step has actually been resumed. Fan-out changes *who* gets notified once a step opens, not *when*.

**Alternatives considered:**
- Leave it as pull-only for pool approvals (the original design) — rejected once real-mode testing showed the actual user-facing cost: a chain that silently stops updating anyone after the first step doesn't demonstrate "event-driven automation" convincingly in a demo, whatever the backend state machine is doing correctly underneath.
- Add real claim/assignment semantics (first pool member to view the approval becomes its assigned owner, notified individually going forward) — more correct for a real multi-person team, meaningfully more code (a new state transition, a new audit event type, a UI affordance for "claim this"), and this project's non-goals explicitly rule out building infrastructure sized for a scale (a real IT department) this V1 doesn't have.
- Notify only the first user returned by `list_by_role`, arbitrarily — rejected as strictly worse than notifying everyone: it reintroduces a single point of failure (what if that specific person is out) without saving any meaningful complexity over just fanning out, since this project has no ordering semantics between pool members to justify picking one.

**Consequences:** Every seeded role (manager, IT, security) now produces a visible Slack ping the moment its step opens, in strict sequence — matches the demo's actual narrative ("approval chain that moves") and is directly testable end-to-end (see the updated `test_role_pool_approval_notifies_every_user_with_that_role` in `backend/tests/test_notifications.py`, which replaced the prior test asserting the opposite behavior). The known limitation — this doesn't scale past "one person effectively owns each role" without further design work — is accepted and documented here rather than solved, consistent with Principle 1 (enterprise realism, not enterprise scale).
