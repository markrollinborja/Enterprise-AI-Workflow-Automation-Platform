# ADR-0016: Integration Connections Store a Credential Reference, Never a Credential; One Connection Row Per Provider Regardless of Transport

**Status:** Accepted — 2026-08-10

**Context:** V2 Module 1 needs one place that answers "is Salesforce working right now?" and "when did it start failing?" for every external system the platform talks to — Salesforce, n8n, Keycloak, Microsoft Graph, SCIM clients, and the MCP-routed providers (Jira, Slack, Google Calendar) V1 already integrates. Two design questions had to be settled before writing `IntegrationConnection`: what this table stores about authentication, and which providers get a row in it at all.

**Decision (secrets):** `IntegrationConnection.credential_ref` stores the *name of the environment variable* holding a connection's credential (e.g. `"SALESFORCE_CLIENT_SECRET"`), never the credential's value. Nothing in this table, or in `HealthCheckResult`, ever holds a token, password, or client secret — `last_error_summary` and `error_summary` are redacted at construction time by `app/core/provider_errors.py` before they reach a row. A database dump of either table is therefore safe to attach to a bug report or show in a demo.

This is a deliberate stop at environment-variable indirection, not an attempt to simulate a real secrets manager. A production deployment of this platform would put credentials in a KMS or a secrets manager (Vault, AWS Secrets Manager) and have `credential_ref` resolve there instead of to `os.environ`; building that machinery for a portfolio project would be effort spent on infrastructure nobody operates, not on the integration-reliability problem this module exists to demonstrate. The honest middle ground is a design that never has a code path capable of persisting a secret, whatever the eventual credential store turns out to be.

**Decision (which providers get a row):** Every provider the platform talks to gets an `IntegrationConnection` row, including Jira, Slack, and Google Calendar — already reachable in V1 through MCP, and not being re-routed by this module. A connection row is an operational record, not a transport: "which of my integrations is unhealthy right now?" is a question the support console (Module 8) has to answer uniformly across all of them, and a health grid with three unexplained gaps because those three happen to go through MCP is worse than one that is simply complete. `SCIM_CLIENT` is the one inbound member — an external identity provider calling *this* platform, not the reverse — and it earns a row for the same reason: its credentials expire and its requests fail, and someone has to see that on the same grid as everything else.

**Alternatives considered:**
- Store credentials encrypted in the row, with the encryption key held elsewhere — rejected as the worst of both worlds: it looks like real secret management (inviting the assumption that it is), while a portfolio project has nowhere safe to keep the encryption key that isn't itself just another environment variable. Indirection that is honestly incomplete beats encryption that is falsely reassuring.
- Give MCP-routed providers (Jira, Slack, Google Calendar) no connection row, since MCP already tracks their calls via `MCPToolExecution` — rejected because it fragments the one dashboard this module exists to build: an operator would have to know which providers to check in the support console and which to check somewhere else, exactly the seam Module 1 is meant to remove.
- One boolean `is_healthy` column instead of the `ConnectionStatus`/`HealthStatus` split — rejected in the model itself (see `app/models/enums.py::ConnectionStatus`) for the same reason: administrative intent ("the operator turned this off") and observed state ("the last check failed") are different facts, and collapsing them loses the "ENABLED but UNHEALTHY" case that is precisely what should page someone.

**Consequences:** No call site can accidentally persist a secret through this table — the column that would hold one doesn't exist. Adding a new provider (Phases 2–6) means adding a `ProviderType` member and pointing its adapter at the right `credential_ref`, not inventing new storage. The cost is that resolving a credential still ultimately reads an environment variable in every deployment of this project, which is explicitly named here as the thing a real production deployment must replace, not a solved problem.

**See also:** `app/models/integration.py`, `app/models/enums.py` (`ProviderType`, `ConnectionStatus`, `HealthStatus`), `app/core/provider_errors.py` (redaction applied before anything reaches `last_error_summary`).
